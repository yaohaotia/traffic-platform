# P5 审核工单与复核设计

状态：设计已落盘，尚未实现。P4 正式关卡通过前，不新增 P5 业务代码或数据库迁移。

## 1. 阶段边界

P4 已定义 `${namespace}.completed` 队列接收 `DETECTION_COMPLETED`。检测低风险将报告置为 `WAITING_REVIEW`，高风险置为 `RISK_REVIEW`。P5 消费该事件并创建人工工单，不重新调用模型，也不直接发奖励。

模型高风险只是复核依据，不是用户造假结论。P5 不自动扣信誉、不自动认定交通违章、不把人工批准等同于资金到账。P6 才接入预算与奖励订单；P7 才接入 XXL-JOB 的生产调度。

## 2. 数据模型（拟 V5）

### review_task

| 字段 | 含义 |
| --- | --- |
| id | 服务端 UUID，API 工单标识 |
| report_id | UNIQUE，一条报告只有一个主工单，阶段变化沿用此工单 |
| source_event_id / source_detection_version | 创建来源事件与当时成功检测版本 |
| region_code | 从报告复制的受理区域，不接受客户端指定 |
| stage | PRIMARY / RECHECK |
| status | READY / CLAIMED / APPROVED / REJECTED / MANUAL_REQUIRED |
| version | 每次领取、转派、升级复核或终审递增 |
| assignee_id | 当前领取人；READY 时为空 |
| lease_token / lease_until | 本次领取凭证与数据库绝对期限 |
| primary_reviewer_id | 普通审核升级复核时保存首审人，防同人复核 |
| transfer_count | 自动超时回收次数，设配置上限 |
| created_at / updated_at / decided_at | 数据库 UTC 时间，微秒精度 |

`review_decision` 保存不可变审核记录：id、task_id、task_version、stage、actor_id、decision、reason、created_at。UNIQUE(task_id, task_version) 防同版本重复决议；不通过删除旧决议实现改判。

`review_audit` 保存 CREATED、CLAIMED、EXPIRED、TRANSFERRED、ESCALATED、APPROVED、REJECTED、MANUAL_REQUIRED 等操作，含操作人、前后版本、原因、时间。审计与对应业务变更同事务，不能先成功写状态再异步补日志。

`message_inbox`：consumer_name、event_id 复合主键，另存 aggregate_id、outcome、processed_at。去重记录与创建工单同事务。事件为检测完成时使用固定 consumer_name，例如 `review-task-creation-v1`。

索引：review_task(region_code,status,stage,created_at)、review_task(assignee_id,status)、review_task(status,lease_until)。相关表使用 InnoDB，与报告和身份表保留外键。

## 3. 完成事件消费

1. 只接收 schemaVersion=1、eventType=DETECTION_COMPLETED、合法 UUID/正数 ID 的消息；限制消息长度，不记录原始 payload。
2. 在数据库核对 source outbox_event、detection_task、traffic_report 与事件 taskId/reportId/evidenceId/userId 一致；成功检测状态和待人工审核状态以数据库为准，不信任消息中附加的风险字段。
3. 在短事务中锁报告，检查 Inbox 与现有工单：已处理事件直接返回幂等结果；另一个有效事件已创建该报告工单时也不再创建第二个工单。
4. WAITING_REVIEW 创建 PRIMARY/READY；RISK_REVIEW 创建 RECHECK/READY，后者要求专门复核权限。保存 source_detection_version，写 CREATED 审计与 Inbox 后提交。
5. 事务返回成功后才能 ACK。数据库异常向监听容器抛出并保留消息；非法或与来源不匹配的消息 reject 到真实死信队列。ACK 丢失后再次投递只能命中 Inbox/报告唯一键，不重复建单。

锁顺序统一为报告 → 工单 → 必要的账户/预算资源，所有写路径保持一致。API 可以先只读查 taskId→reportId，再在事务内按上述顺序重新读取并校验；不要让领取和消费采用相反锁序。

P4 原监听器 `trafficDetectionListener` 保留不变。P5 使用独立监听器 ID `trafficReviewCreationListener`，消费现有 completed 队列。增加 `traffic.review.listener-enabled` 开关：local 可启用，基础/P3/P4 测试默认关闭，P5 集成测试显式启用并使用独立 namespace。开关不能作为失败时静默跳过验收的手段。

## 4. 权限与归属

保留 P3 `report:review` 的区域内线索查看能力；新增 `review:claim`、`review:decide`、`review:recheck`、`review:manage`。

- 领取 PRIMARY 需要 review:claim + review:decide，领取 RECHECK 需要 review:claim + review:recheck。
- 所有领取与决议都必须绑定报告区域，且 actorId != 报告提交人。拥有管理员角色也不能绕过禁止自审。
- 普通首审请求复核后，首审人不能领取或提交此工单的 RECHECK 阶段，即使后来获得复核权限。
- 模型直接判高风险时尚无人工首审人，工单直接进入 RECHECK；专门复核权限与普通审核权限不同，不伪造一次不存在的人工首审记录。
- 管理权限用于转派、查看积压和处理 MANUAL_REQUIRED，不等于代替他人提交决议。管理员可以跨区域查看运维概况；实际审核仍需区域与当前领取身份校验。
- 公共 HTTP 参数不能传 actorId、regionCode 或 canManage 来扩大权限；身份和权限从验证后的服务端上下文读取。

## 5. 状态、领取与超时

主流程：

```text
READY --领取--> CLAIMED --APPROVE--> APPROVED
                         --REJECT--> REJECTED
                         --REQUEST_RECHECK--> READY(stage=RECHECK)
CLAIMED --租约到期--> READY(version+1, transfer_count+1)
                           --达到回收上限--> MANUAL_REQUIRED
```

只有 PRIMARY 可 REQUEST_RECHECK；复核不允许无限再次升级。RECHECK 的终审人必须符合专门权限和不同首审人的条件。审核理由必填并限长，尤其是驳回、升级、转派与人工接管操作。

领取请求携带 expectedVersion。服务在事务中验证 READY、版本、区域、角色、自审限制后，用数据库条件更新写 assignee、随机 lease_token、lease_until 并 version+1。只返回该次领取的新版本与 token；列表、普通详情、报告拥有者进度接口不得暴露其他人的领取 token。

提交决议携带 version 与 leaseToken。检查当前 CLAIMED、当前领取人、数据库时间仍在租约内、版本/token 完全匹配。终审状态不能反转；同一次决议内容完全相同时可幂等返回，冲突内容409。重复请求的幂等匹配包含 actor、版本、decision、reason，不能只看终态相同就接受其他人请求。

超时回收使用短事务与 CAS。旧领取人即使稍后返回也只能得到409，不能覆盖新领取人的结果。限制每轮扫描数量和自动回收次数，避免坏工单无限重排或饿死新工单；超限进入 MANUAL_REQUIRED，管理员显式处理并留下审计。P5 提供可测试的 application 方法，P7 再由 XXL-JOB 调用；P5 不伪造“已经接入分布式调度”。

## 6. 拟议 HTTP API

统一前缀 `/api/v1/review-tasks`，错误沿用 ApiError；size 默认20、上限100，身份/区域过滤在服务端。

| API | 请求/行为 |
| --- | --- |
| GET /review-tasks?status=READY&stage=PRIMARY&page=1&size=20 | 仅返回当前审核员可处理的区域及阶段；可过滤自身已领取任务 |
| GET /review-tasks/{id} | 区域内授权审核员查看工单、证据元数据和风险信息；隐藏内部 token 与敏感用户信息 |
| POST /review-tasks/{id}/claim | `{expectedVersion}`，成功返回新 version、leaseToken、leaseUntil |
| POST /review-tasks/{id}/decisions | `{version,leaseToken,decision,reason}`，decision=APPROVE/REJECT/REQUEST_RECHECK |
| POST /review-tasks/{id}/reassign | 管理员显式转派/解锁，`{expectedVersion,targetReviewerId,reason}`；目标必须满足区域、阶段、自审/首审隔离规则 |
| GET /review-tasks/{id}/audit | 区域内授权查询不可变审核轨迹；不返回内部错误堆栈或令牌 |

成功查询/领取/决议200；参数400、权限403、资源404、版本/租约/终态冲突409。报告提交人通过已有报告进度接口看审核状态，不通过审核员私有接口取得领取信息。

## 7. P6 的批准与预算事务边界

P5 审核批准只是人工决议；reward_status 仍不能被置为 PAID/ISSUED。P5 可以记录 REVIEW_DECIDED 事件及明确的待激励意图，但不能让用户看到“奖励已到账”。

推荐在审核 application 服务的批准分支定义 `ApprovalPreparationPort.prepare(ApprovedDecision)`。它必须在**调用方现有数据库事务**中执行，参数包含 reportId、taskId、taskVersion、审核人、campaignId、userId、奖励快照和稳定 decisionId，禁止自行开启 REQUIRES_NEW 或调用外部 HTTP/MQ。

P5 的阶段实现只记录可追踪的批准意图（例如 review_approval_intent，状态 AWAITING_REWARD_INTEGRATION），明确没有预算预留或发款。P6 在此端口补齐：

1. 同事务核验任务预算，用条件更新预留奖励金额。
2. 创建唯一来源为 decisionId/reportId 的 reward_order，禁止同一报告重复生成奖励。
3. 写奖励发放 Outbox，再写 APPROVED 工单/报告状态与决议审计。
4. 任一步失败，整个批准事务回滚；预算不足返回明确409并保留可处理的审核状态，不把有效线索改成无效。

P6 不能改成“先提交审核批准，再独立事务补预算”，那会重新引入跨步骤不一致。P5 阶段产生的待激励意图，需要 P6 显式、有幂等键且可审计的激活/迁移流程；不能静默补发。若 P6 选择直接扩展同一 application 服务而不使用端口，也必须保持上述单事务边界，并重跑全部 P5 测试。

## 8. 必须的真实服务验收

以下是未来 P5 实现的门槛，不是已执行结果。使用真实 MySQL、Redis、RabbitMQ 与独立 namespace，不用 mock 替代事务或消息证明。

1. 同一 DETECTION_COMPLETED 重复投递、提交后断连未 ACK、两个消费者并发投递：仅一个 review_task，一条有效创建审计，Inbox 去重正确。
2. 错误 schema/type/事件来源/ID 不匹配进入 DLQ；数据库写失败不能 ACK，也不能留下孤立 Inbox。
3. 两审核员同时领取同一版本，仅一个成功；成功领取人/token/version 对应正确。
4. 普通用户、跨区域审核员、报告提交人均不能领取/处理；管理员也不能自审。
5. 普通审核权限不能处理 RECHECK；首审人不能复核自己的决定；符合条件的另一复核员可以终审。
6. 租约到期后旧 token 被拒绝；回收后版本递增，新领取人的结果不会被旧请求覆盖。
7. 重复同一决议只记录一次；不同理由或不同决定不能借终态幂等通过；终态不能反转。
8. 并发回收、转派与审核提交只有一种有效结果，审计与状态一致；达到回收上限进入人工处理。
9. 高风险事件只产生复核工单，不扣信誉、不发奖励；低风险人工升级复核保留真实首审来源。
10. APPROVE 时 P5 只记录批准意图，账户余额、预算和奖励流水均未改变；P6 再验证预算/奖励/批准的共同回滚。
11. 列表有界分页、身份注入无效、详情不泄露其他人的领取 token；历史工单查询遵守区域限制。
12. P1～P4 与 Python 协议测试全量回归，零失败、错误和跳过，阶段报告归档后才能进入 P6。

## 9. 实施前必须同步的内容

实现时先冻结 V5/API 契约并让测试代理依据契约并行写验收，再写生产代码；P4 gate 通过是前置条件。P4 completed 队列应复用，不能另建一个永远收不到现有消息的队列；P4 的消费者开关、来源验证、事件 ID 和 DB 状态须一起核对。新角色/权限仅在显式初始化新账号或受控迁移中赋予，不以每次启动重置现有权限。
