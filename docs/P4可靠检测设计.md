# P4 可靠检测设计（待实施）

制定日期：2026-11-03。本文承接 `项目重构计划书.md` 的 P4 和 `../traffic-platform/P3-contract.md`。当前 P3 尚未通过验收，本文件仅保存设计，不代表 P4 已实现；P3 全部测试通过后才能开始 P4 代码。

## 1. 职责与原则

MySQL 的 detection_task 是执行真相，RabbitMQ 是任务唤醒通道。持久化任务负责恢复，消息重复不能产生第二次有效结果。publisher confirm 仅说明 broker 接受，不能代表模型已执行。HTTP 调用、图片读取、MQ 投递均不得处于数据库长事务中。

首轮仍为模块化单体：outbox 投递器、Rabbit 监听器、检测编排、任务事务服务、模型 HTTP 适配器各自分离。P4 可使用有界定时扫描驱动补投与回收，P7 再接 XXL-JOB；业务幂等不依赖调度器“只运行一次”。

## 2. P3 接口的延续

P3 已冻结：detection_task 的 id 为稳定 UUID，report_id 唯一，status 初始 PENDING，attempt_count/version 初始 0。outbox_event 的 event_id 为稳定 UUID，初始 REPORT_SUBMITTED/PENDING，payload 含 eventId/eventType/taskId/reportId/evidenceId/userId/schemaVersion=1。

消息只携带标识，不含本地路径、临时文件名、用户可控下载 URL、JWT 或图片正文。消费者必须对照数据库核对 task/report/evidence 关系，不能依赖 payload 决定文件路径。schemaVersion 或 eventType 不支持时拒绝到隔离死信通道。

## 4. Outbox 投递协议

1. **短事务领取：** 按到期时间有序取 PENDING 行，使用 FOR UPDATE SKIP LOCKED 或条件更新领取，设置随机 lease_token、lease_until、status=PUBLISHING，并增加投递 attempt_count。事务立即提交。
2. **事务外投递：** 持久化消息发送至 durable exchange/queue，mandatory=true，publisher returns=true，confirm-type=correlated。消息 messageId=稳定 eventId；CorrelationData.id=eventId+本次 leaseToken，区分同一事件的多个投递尝试。
3. **有界等待确认：** 使用 CorrelationData.getFuture()，同时检查 isAck() 和 getReturn()==null；convertAndSend 正常返回不算投递成功。Spring AMQP 4.1 文档保证 return 在该 future 完成前已经填充。
4. **短事务回写：** 仅 WHERE event_id=? AND status=PUBLISHING AND lease_token=? 更新 SENT/published_at。超时、nack、return、断连则记录失败并安排退避；租约已变更的迟到回调忽略。
5. **租约回收：** PUBLISHING 超时恢复可投递状态。broker 已接受但数据库尚未记录 SENT 时允许重复投递，由任务幂等承担。

先采用有界批次、逐事件确认即可，避免在首轮引入复杂并行 callback 管理。达到投递次数上限进入 DEAD 并可查询/人工重投，不能静默丢弃。人工重投沿用原 eventId 和不可变 payload，重建投递租约，不伪造新业务事件。

## 5. 消费与检测的三个事务边界

### A. 短事务领取

监听器校验协议后，按 taskId 锁定或条件更新任务。仅 PENDING 可领取；设置 RUNNING、随机执行 leaseToken，version+1、attempt_count+1，并确定 lease_until。读取不可变 report/evidence 元数据后提交事务，返回执行快照。

SUCCEEDED/DEAD 的重复消息直接确认。RETRY_WAIT 未到期或已有有效 RUNNING 租约的重复信号也可确认，因为数据库恢复任务负责补发；此策略必须同时交付租约回收/待处理对账扫描，不能只 ACK 后不再恢复。

不要在领取时将 consumer/inbox 记录标为 DONE，否则领取提交后进程崩溃时 redelivery 会永久被跳过。检测场景可直接以唯一 taskId、状态、version 和租约实现幂等，不必为了凑组件另加无意义的 DONE 表。

### B. 事务外模型调用

从受信任的 StorageAdapter 按数据库 object_key 读取文件，向固定配置的模型基地址发送 multipart。设置连接/读取/总时限，限制并发、prefetch 和响应大小。模型调用前后都不能持有数据库事务；可用 TransactionSynchronizationManager 及阻塞 HTTP 桩测试证明这一点。

执行租约必须大于请求的硬超时加合理余量。首轮使用固定有界请求，无需复杂心跳；若后续支持长视频或超长模型请求，再增加带 token 的租约续期。HTTP 线程本身超时不保证服务器停止计算，所以迟到结果检查仍是必需。

### C. 短事务提交结果

只允许 WHERE task.id=? AND status=RUNNING AND version=? AND lease_token=? AND lease_until>数据库当前时间 写入结果。满足后在同一事务：更新 task 终态/结果、更新 report 检测与审核状态、保存后续业务事件（如 DETECTION_COMPLETED）。影响行数为0表示旧执行结果，忽略且不能再更新 report。

结果提交后才 ACK 原消息。提交成功而 ACK 前连接断开时，redelivery 看见终态只确认，不再次推理/建单。

## 6. 重试、恢复与死信

- 可重试：网络断连、超时、模型暂时不可用、明确可恢复的5xx。短事务把当前 token 对应任务转 RETRY_WAIT，设置 next_attempt_at，保存失败原因，然后 ACK 原信号。
- 永久失败：证据缺失/损坏、协议不支持、模型响应类型或分数非法等。任务进入 DEAD，保留原因和处理入口；消息本身无效时 basicReject/basicNack(requeue=false) 进入 broker DLQ。
- 次数上限：按真实领取/执行计数，不能按 Rabbit redelivery 次数计数；例如最多5次，具体值可配置。指数退避应有上限和随机抖动。
- 到期重试：扫描 RETRY_WAIT 到期任务，短事务将其转 PENDING 并创建新的 Outbox 唤醒事件，防止提交状态后未发消息。每次重试信号只生成一次，可加 outbox dedup_key/task dispatch_no 唯一约束。
- 崩溃回收：RUNNING 租约过期后转 RETRY_WAIT/DEAD，清旧 token；旧执行即使随后成功也不能提交。
- 漏信号对账：对长时间 PENDING 且无在途租约的任务，有界重新产生唤醒事件，防止 broker 侧消息消失或基础设施错误进入 DLQ 后永久挂起。重复信号由数据库领取约束去重。
- 公平性：按 next_attempt_at/创建时间扫描合适状态，而非每次只抓最早5条坏任务；DEAD 不参与自动扫描。
- 数据库故障：监听器不得 ACK 未保存的领取/结果。避免无延迟 nack(requeue=true) 热循环；采用有界容器重试/暂停退避，并由数据库恢复扫描补信号。无效毒消息不能拖住正常任务。
- Rabbit 4.1 基线不依赖4.4才出现的延迟重试特性。不要把默认DLX当成绝对可靠存储；DLX目标缺失会丢消息，关键失败状态必须留在数据库。生产可评估 quorum + at-least-once dead lettering，不能在单节点本地环境宣称高可用。

## 7. 模型 HTTP 契约

建议新增 `POST /api/v1/detect` multipart字段 `image`，保留旧 `/detect` URL接口供旧项目使用。新后端只调用 multipart，不为本地证据新增公开任意文件下载接口，也不把用户输入URL交给模型下载。

请求可带 taskId/version/requestId 追踪，不能依赖它们免除Java端幂等。响应建议：`schemaVersion=1, score, threshold, modelVersion, isAiGenerated`；score/threshold必须是有限数且位于[0,1]，boolean与阈值关系一致。模型输出是风险分数，不是数据集 accuracy/AP。响应非法应失败而不是默认“真实图片”。

Python侧限制上传体积/像素、使用原 processing_RPTC 预处理及固定权重版本，不为性能改变标签方向。模型初始化与推理逻辑可抽离以便协议测试；P4 Java HTTP桩验证协议，P8才验证真实解释器/权重效果。所有Python命令继续固定 `/d/soft/Anaconda/python`。

## 8. 后台 API 建议

- `GET /api/v1/detection-tasks/{id}`：有 detection:manage 或对应区域审核权限才可查看，owner仅查看脱敏进度；不暴露文件系统路径或堆栈。
- `POST /api/v1/detection-tasks/{id}/retry`：detection:manage，必填reason；仅 DEAD/允许的RETRY_WAIT，短事务重置可执行状态、递增version并产生新Outbox。不能直接重跑已经人工终审的线索。
- `GET /api/v1/outbox-events?status=DEAD`、`POST /api/v1/outbox-events/{id}/retry`：运维权限，原eventId、不可变payload、操作审计。
- 队列配置、modelBaseUrl、最大重试次数不能由普通HTTP请求随意指定。

## 9. P4 测试矩阵

默认 `verify` 必须包含 `ReliableDetectionIntegrationTest`，使用真实 MySQL、Redis、RabbitMQ和本机HTTP桩，无skip；前序 Foundation/Security/Report 测试继续回归。

| 场景 | 必须证明 |
| --- | --- |
| 正常投递/推理 | Outbox确认后SENT，task成功，report进正确人工审核状态，模型版本/分数持久化 |
| Rabbit停止/恢复 | report/task/outbox已提交；不能假SENT；恢复后可以投递 |
| 不可路由return | broker可能ack但event不能SENT，保留失败原因/退避 |
| 发布确认超时/迟到回调 | 旧lease回调不能覆盖新投递状态 |
| 多实例/重复消息 | 同task只一条有效领取与结果，无重复后续事件 |
| 事务边界 | HTTP桩阻塞时数据库事务已关闭；其他任务不被该任务行锁长时间阻塞 |
| 结果提交后未ACK | 关闭消费者channel导致重投，模型调用计数/后续事件仍一次 |
| claim后进程/执行器退出 | 租约过期回收，后续新token可完成 |
| 过期结果 | 新token已领取后，旧请求返回不改变task/report |
| 有限重试/毒消息 | 达上限DEAD，不饿死后面的正常任务；无效协议进入隔离队列 |
| 人工重跑 | 权限/区域/理由校验，重复操作不产生重复在途任务 |
| 模型非法响应 | 缺字段、越界、NaN、非JSON、过大响应、超时均不能变成成功或直接处罚 |

测试应显式控制监听器/扫描器启停，避免P4消费者在P3原子落库测试中异步修改待处理记录。各suite使用独立队列命名空间或测试vhost，结束时只清理自己资源，不能 purge 用户既有队列或 FLUSHALL。
