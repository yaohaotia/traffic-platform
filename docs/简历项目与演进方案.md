# 项目定位与简历文本

## 项目名称

交通违章举报审核与激励平台。定位 Java 后端学习项目，AI 是证据合成风险筛查的外部能力。原简历的“云边协同机动车违章识别”在当前代码中缺少边缘部署和违章模型支撑，建议替换；若另有部署记录和代码，再据实补回。

## 可用于简历的项目段落

以下按当前代码编写；新增改造应在完成本文验收后使用。项目时间沿用你的实际开发记录，本轮新增工作单独记录，不向过去倒填。

**交通违章举报审核与激励平台 | Java 后端开发（个人学习项目）**

**技术栈：** Java、Spring Boot、MyBatis-Plus、MySQL、Redis、Sa-Token、Spring Scheduling、七牛云对象存储、Vue、Element UI、ECharts；Python、Flask、PyTorch（模型服务）。

**项目描述：** 面向交通违章线索收集与审核场景，提供图片上传、AI 合成风险筛查、审核员人工核验、奖励入账、提现审批和信誉管理，采用前后端分离架构，通过 HTTP 接入独立模型服务。

- 设计举报状态流转约束，结合数据库行锁与本地事务，实现重复审核保护，避免同一举报重复发奖及非法终态反转。
- 完善奖励与提现的资金处理，使用 BigDecimal、余额校验、账户行锁和事务，保证业务状态、账户余额与流水在同一事务内更新；退款金额以服务端记录为准。
- 基于数据库待检测记录与定时扫描解耦提交和推理流程，检测失败保留待处理状态，支持应用重启后继续处理；通过角色与任务归属检查限制人工审核操作。
- 接入 PatchCraft/RPTC 图片合成风险检测，修正单图推理结果契约，复用模型预处理，并完成举报、审核、账户及运营统计页面的前后端对接。

不要写未经测试的 QPS、并发量、准确率、效率提升百分比，也不要将引入已有模型写成自主研发模型。未做真实边缘部署、自动违章识别、支付渠道对接时不写这些能力。

## 后续完整工程栈的落地顺序

1. **业务正确性与复现：** 补银行卡归属校验、统一角色授权、人工复核、业务流水唯一键、请求幂等键；完成真实 MySQL 事务与并发测试、Python 模型契约联调。编写安全的本地示例配置，整理可重复导入的演示数据。
2. **检测可靠性：** 新建检测任务表和 Outbox。提交举报与保存 Outbox 同事务；投递任务记录发送状态，MQ 消费者用 taskId 与条件更新防重。设最大重试次数、指数退避、死信和人工重试入口；不用定时扫描一直重试坏数据。
3. **运行与可观察性：** 补 Docker Compose、Nginx 代理、健康检查、结构化日志和请求追踪 ID。采集待检测数量、失败次数、耗时分布、审核积压、账务差异；再按实际需求接入 Prometheus/Grafana 与 XXL-JOB。
4. **查询优化：** 先评估索引和 SQL；确定复杂多字段检索确有需求后再用 Elasticsearch。MySQL 是主数据源，ES 可重建，必须设计同步失败补偿。

以上每个阶段只有运行和验收后，才把新增技术写入简历。现有单体业务适合先吃透事务与并发，再扩展消息与运维。

## 必须做的演示验收

- 重复或并发审核同一举报，余额只增加一次，奖励流水只出现一次。
- 同一用户同时发起两笔总额超过余额的提现，只有满足余额条件的申请成功；余额不能为负。
- 对同一提现重复拒绝，只退款一次；先通过再拒绝被拒绝；客户端篡改金额和用户不影响退款对象。
- 审核员 A 不能审核 B 的任务；普通用户无法调用人工审核和提现审批接口。
- 模型服务关闭时，上传仍保存待检测记录；模型恢复后重新处理；错误响应不能作为真实图片或 AI 图片的有效结论。
- 校验两张已知样例图片的置信度与类别，核对标签方向；数据集 accuracy/AP 只能用于离线评估，不可作为单图输出。
- 现有单元测试验证边界分支，不证明真实数据库并发隔离。上述数据库与端到端验收仍需在本地依赖就绪后执行。
