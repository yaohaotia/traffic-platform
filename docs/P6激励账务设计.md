# P6 激励账务与站内通知设计

制定日期：2026-11-04。仅在 P5 正式测试关卡通过后实施。

## 业务边界

奖励是校园/园区线索激励，不代替交管处罚。模型不发奖，人工终审通过才产生奖励。提现只模拟申请、冻结、审批结算，不接银行或第三方支付，不收集银行卡信息。

## 实施顺序

1. V6 增加预算占用/支出、奖励订单、预算流水、钱包及不可变流水、补偿单、模拟提现单和站内通知；保留 V1—V5 原迁移。
2. 实现 P5 的 ApprovalPreparationPort：在审核现有事务内预留预算、保存唯一奖励订单和 Outbox。预算不足返回 409，整次终审回滚，保留领取状态；通过独立授权、带原因和幂等号的预算追加操作解决。
3. 奖励消费者读取数据库中的规范事件与订单，短事务完成占用转支出、钱包入账、流水及结果 Outbox；提交之后才 ACK。唯一业务来源和状态条件更新共同保证重复投递不重复到账。
4. 取消未发放订单释放占用；已发放更正创建补偿单，保留原入账流水。余额足够才冲回并退还预算，余额不足标记人工追偿，不制造负可用余额或虚构预算退款。
5. 独立通知队列订阅审核及奖励事件，不能与奖励消费者竞争同一个队列。通知唯一键按收件人和来源事件去重，已读只允许本人操作。
6. 模拟提现采用“可用转冻结→独立审批→模拟支出/驳回释放”，全程唯一请求号、状态检查与流水；申请人不得审批自己的提现。
7. 提供只读对账：预算占用/支出与订单/预算流水一致；钱包余额/冻结与不可变流水合计一致。恢复入口有界扫描数据库，不能依赖浏览器触发发奖。
8. P6 专项测试通过后执行 clean verify 和 Python 协议回归；归档报告后才进入 P7。

## 一致性与安全约束

- 所有金额 BigDecimal/DECIMAL(12,2)，大于零、最多两位小数；MySQL 约束防止负余额及超预算。
- 审核、奖励、补偿按报告→奖励订单→征集预算→钱包顺序加锁；提现只锁钱包后锁自身单据，不反向请求报告/预算锁。
- 资金事实保存在 MySQL。Redis 只负责身份与访问控制，不作为唯一余额或资金锁。
- 同一报告最多一个奖励订单；同一订单最多一次 CREDIT 和一次 REVERSAL；补偿单唯一关联原订单。
- P5 历史 AWAITING_REWARD_INTEGRATION 意图不能静默发奖，必须由 reward:manage 显式激活，记录操作人和原因，重复激活返回原订单。
- HTTP 不接受自报 userId/余额；钱包、流水、通知、提现按当前身份过滤，管理操作还检查对应区域。原始存储路径、租约令牌、凭据均不进入通知。
- 数据库异常整事务回滚，消息保留重试；毒消息只有可靠投到死信后才能移除，不能 ACK 丢失。

## 必须通过的真实服务检查

并发审批最后一份预算只成功一次；审核/预算/订单/Outbox 同事务故障回滚；实际 RabbitMQ 重复投递和未 ACK 重投只入账一次；取消与入账竞态结果一致；重复补偿只冲回一次；冻结余额不能被补偿或再次提现；自审批与跨用户/跨区域操作拒绝；历史意图显式激活幂等；通知独立订阅且去重；预算和钱包对账无差异；真实数据库写入失败后消息可恢复。
